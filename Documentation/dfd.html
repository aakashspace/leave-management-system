📊 DFD Level 1 — System Decomposed into 4 Processes
┌──────────┐ ┌──────────────────────────┐ │ EMPLOYEE │──Registration──────►│ 1.0 User Management │◄──Approval Decision──┐ │ │◄─Account Status─────│ │──Pending Users──────►│ └──────────┘ └──────────┬───────────────┘ │ │ R/W Users (D1), Departments (D2) │ ┌──────────┐ ┌──────────▼───────────────┐ │ │ EMPLOYEE │──Leave Application─►│ 2.0 Leave Application │ │ │ │◄─Leave Status───────│ │ ADMIN └──────────┘ └──────────┬───────────────┘ │ │ R/W Users (D1), Leave Types (D3), │ │ Leave Requests (D4) │ ┌──────────▼───────────────┐ │ │ 3.0 Admin Review │◄─Approve/Reject──────┘ │ & Management │──Leave Queue────────►│ └──────────┬───────────────┘ │ │ R/W D1, D3, D4 │ ┌──────────▼───────────────┐ │ │ 4.0 Reporting & │◄─Report Request──────┘ │ Analytics │──Stats/Reports──────► └──────────────────────────┘ R Users(D1), Depts(D2), Requests(D4)
1.0 User ManagementHandles registration (→ D1), admin approval/rejection, profile edits. Reads D2 for department assignment.
2.0 Leave ApplicationValidates dates, calculates working days, checks balance in D1, assigns priority, writes to D4.
3.0 Admin Review & ManagementReads D4 pending requests sorted by priority. Approves/rejects, updates D4 and D1 balances. CRUD on D3 and D2.
4.0 Reporting & AnalyticsAggregates D4 joined with D1 and D2. Returns stats by type, department, and employee.
📊 DFD Level 2 — Each Level-1 Process Broken Down

Process 1.0 — User Management

1.1 Register UserEmployee submits name, email, dept → Express creates user in D1 (users) with status='pending'
1.2 Select / Authenticate UserUser picks account from dropdown → system loads from D1 → Pinia store set → navigate to /employee or /admin
1.3 Approve UserAdmin approves → status='approved' in D1 → system reads all active types from D3 → initialises leave_balances array in D1
1.4 Reject UserAdmin rejects → status='rejected' in D1. User cannot access system.
1.5 Edit ProfileEmployee updates name/dept → PUT /api/users/:id → D1 updated → Pinia store refreshed

Process 2.0 — Leave Application

2.1 Select Leave TypeEmployee picks type → system reads D3 → shows remaining balance from D1 leave_balances
2.2 Validate DatesEmployee enters start/end → system checks start ≤ end → calculates Mon–Fri working days only
2.3 Check BalanceIf is_paid=true → reads D1 leave_balances → if requested_days > remaining_days → return error "Insufficient balance"
2.4 Auto-Assign PriorityReads leave type name → Sick/Emergency → high · Casual → medium · others → low
2.5 Create Leave RequestWrites new document to D4 (leave_requests) with status='pending'
2.6 Cancel RequestEmployee cancels pending → D4 status set to 'rejected', admin_comment = 'Cancelled by employee'

Process 3.0 — Admin Review

3.1 Fetch Pending RequestsAdmin opens dashboard → reads D4 where status='pending' → JavaScript sort: high → medium → low
3.2 Approve RequestAdmin approves → if is_paid: atomic $inc on D1 leave_balances → D4 status='approved', admin_comment saved
3.3 Reject RequestAdmin rejects → D4 status='rejected' → no balance change in D1
3.4 Manage Leave TypesAdmin CRUD on D3 → add/edit/deactivate leave types (soft delete via is_active=false)
3.5 Manage DepartmentsAdmin CRUD on D2 → add/edit/delete departments

Process 4.0 — Reporting

4.1 Dashboard StatsCount from D1: total approved employees, pending approvals. Count from D4: by status, high priority pending.
4.2 Leave Type StatsMongoDB $group on D4 by leave_type_name → count and totalDays per type
4.3 Department Stats$lookup D4→D1→D2 → $group by dept_name → totalRequests, totalDays, approved, pending, rejected
4.4 Employee Stats$lookup D4→D1 → $group by user_id → totalRequests, totalDays, approved count, approval rate %
📊 DFD Level 3 — Critical Process Deep-Dive

Process 2.3 — Check Balance (Most Critical Business Logic)

[Employee Request] ──► 2.3.1 Read User Doc ──► 2.3.2 Find Matching Balance │ │ Query D1 by Search leave_balances[] user_id where leave_type_id matches │ ┌───────────▼────────────┐ │ is_paid = false? │ │ YES → Skip to 2.5 │ │ NO → Continue │ └───────────┬────────────┘ │ ┌───────────▼────────────┐ │ 2.3.3 Compare Values │ │ requested > remaining? │ │ YES → Error 400 │ │ NO → Pass │ └───────────┬────────────┘ │ ┌───────────▼────────────┐ │ 2.3.4 Pass Validation │ │ Proceed to 2.4 │ │ (Auto-Assign Priority) │ └────────────────────────┘

Process 3.2 — Approve Leave + Atomic Balance Deduction

[Admin Approves] ──► 3.2.1 Fetch Leave Request ──► 3.2.2 Check is_paid │ Query D4 by id │ Validate status │ is_paid = false? = 'pending' ┌──────▼─────────────────────┐ │ Skip balance update (unpaid)│ └──────────────────┬─────────┘ │ 3.2.3 Atomic DB Update │ ─────────────────────── │ MongoDB $inc operator: │ leave_balances.$.used_days += total_days leave_balances.$.remaining_days -= total_days (Single operation — prevents race conditions) │ ┌──────────────────▼─────────┐ │ 3.2.4 Update D4 status │ │ status='approved' │ │ admin_comment saved │ └──────────────────┬─────────┘ │ ┌──────────────────▼─────────┐ │ 3.2.5 Return Response │ │ Updated leave document │ │ sent to Admin Dashboard │ └────────────────────────────┘

Process 1.3 — Approve User + Balance Initialisation

[Admin Approves User] ──► 1.3.1 Fetch Active Leave Types │ Query D3: is_active = true │ Returns: [Annual, Sick, Casual, Maternity, Emergency] │ 1.3.2 Build Balance Array │ For each LeaveType: │ { leave_type_id, leave_type_name, │ total_days: max_paid_days, │ used_days: 0, │ remaining_days: max_paid_days } │ 1.3.3 Update D1 (users) │ status = 'approved' │ leave_balances = built array │ 1.3.4 Return Updated User └─► Admin sees user is now approved

Process 4.3 — Department Stats (MongoDB Aggregation Pipeline)

D4 (leave_requests) │ ├─ Stage 1: $lookup → D1 (users) on: user_id = _id ├─ Stage 2: $unwind → users array (one doc per request) ├─ Stage 3: $lookup → D2 (departments) on: user.dept_id = _id ├─ Stage 4: $unwind → dept array preserveNullAndEmptyArrays=true │ (keeps requests with no dept) ├─ Stage 5: $group → by dept_name │ sum: totalRequests, totalDays │ cond: approved, pending, rejected counts ├─ Stage 6: $sort → totalRequests descending └─ Result: [{ _id: "Engineering", totalRequests: 5, totalDays: 12, ... }]
