🟢 Basic Level — Fundamentals

Core concepts, project overview, and technology basics

Questions 1–15  ·  15 questions

Basic
Q1. What is this project about? What problem does it solve? ›
The Leave Management System (LMS) is a full-stack web application that automates employee leave management. It replaces manual, paper-based or spreadsheet methods with a centralised digital platform. Employees can register, apply for leave, view their balances and history, and track their status. Admins can approve/reject users, configure leave types, manage departments, and view detailed reports. The system eliminates errors in balance calculation, ensures policy enforcement, and provides real-time visibility into leave data.
Basic
Q2. What is the MEVN stack? ›
MEVN stands for MongoDB, Express.js, Vue.js, and Node.js. It is a full-stack JavaScript framework combination. MongoDB is the database, Express.js is the backend web framework running on Node.js, and Vue.js is the frontend framework. All four technologies use JavaScript, which means the same language is used throughout the entire application — from database queries to API logic to UI rendering. It is similar to the MEAN stack but uses Vue.js instead of Angular.
Basic
Q3. What is MongoDB? What type of database is it? ›
MongoDB is a NoSQL document database. Unlike relational databases like MySQL that store data in rows and columns (tables), MongoDB stores data as BSON documents (Binary JSON — similar to JSON objects). Each document can have a flexible structure, and related data can be embedded directly inside a document (like the leave_balances array inside the user document). It is highly scalable and works naturally with JavaScript since the data format matches JSON.
Basic
Q4. What is Node.js? ›
Node.js is a JavaScript runtime environment built on Google Chrome's V8 JavaScript engine. It allows JavaScript to run on the server side (outside the browser). Node.js uses an event-driven, non-blocking I/O model, which means it can handle many simultaneous requests without creating a new thread for each one — making it fast and efficient. In this project, the entire backend server is built on Node.js.
Basic
Q5. What is Express.js? ›
Express.js is a minimal and flexible Node.js web application framework. It provides a thin layer of features for building web applications and APIs — such as routing (defining what happens when a URL is hit), middleware (functions that run between a request and response), and error handling. In this project, Express handles all the API endpoints like POST /api/leave-requests or GET /api/users.
Basic
Q6. What is Vue.js? How is it different from plain HTML/JavaScript? ›
Vue.js is a progressive JavaScript framework for building user interfaces. Unlike plain HTML/JS where you manually update the DOM when data changes, Vue uses a reactive data system — when data changes, the UI automatically updates without you writing DOM manipulation code. It also supports components (reusable building blocks), routing (Vue Router), and state management (Pinia). Vue.js enables building a Single Page Application where the page never fully reloads.
Basic
Q7. What is a REST API? ›
REST (Representational State Transfer) is an architectural style for building APIs. A RESTful API uses standard HTTP methods: GET (retrieve data), POST (create data), PUT (update data), DELETE (remove data). In this project, the Express.js backend exposes RESTful endpoints. For example, GET /api/users retrieves all users, POST /api/leave-requests creates a new leave application. Each response is a JSON object with the structure: { success: true/false, data: ..., message: ... }.
Basic
Q8. What is JSON? ›
JSON stands for JavaScript Object Notation. It is a lightweight, human-readable data format used for storing and transmitting data. In this project, all communication between the Vue.js frontend and the Express.js backend is done via JSON. For example, when an employee submits a leave application, the form data is sent as JSON to the API. The API responds with JSON containing the result. MongoDB also stores data in a JSON-like format called BSON.
Basic
Q9. How do you run this project? ›
To run the project: (1) Ensure Node.js v18+ and MongoDB are installed. (2) Double-click start.bat in the project root. It automatically checks for node_modules, installs if missing, starts MongoDB service, opens two terminal windows (backend on port 5000, frontend on port 5173), and opens the browser. Alternatively, open two terminals: in backend/ run node server.js, in frontend/ run npm run dev. Then open http://localhost:5173 in a browser.
Basic
Q10. What is package.json and what is its purpose? ›
package.json is a configuration file for Node.js projects. It contains: the project name and version, a list of dependencies (packages the project needs, like express, mongoose, cors, vue, axios), devDependencies (tools only needed during development, like nodemon, vite), and scripts (shortcuts for running commands like npm start to start the server or npm run dev to start the Vite dev server). When you run npm install, npm reads package.json and installs all listed packages into node_modules.
Basic
Q11. What is npm? ›
npm stands for Node Package Manager. It is the default package manager for Node.js. It allows developers to install, update, and manage third-party packages/libraries for their projects. For example, npm install express downloads and installs Express.js. npm run dev executes the "dev" script defined in package.json. All packages are stored in the node_modules folder and tracked in package.json.
Basic
Q12. What is the purpose of the .env file? ›
The .env file stores environment variables — configuration values that may differ between environments (development, production). In this project, it contains PORT=5000 (the port Express runs on) and MONGO_URI=mongodb://localhost:27017/lms_db (the MongoDB connection string). Using .env means these values can be changed without modifying the source code, and sensitive values (like database passwords in production) are kept out of version control by adding .env to .gitignore.
Basic
Q13. How many collections does MongoDB have in this project? Name them. ›
The project uses 4 collections in the lms_db database: (1) users — stores employee and admin accounts with embedded leave balances. (2) departments — stores department names like Engineering, HR, Marketing, Finance. (3) leave_types — stores leave type configurations like Sick Leave (10 days), Annual Leave (15 days), etc. (4) leave_requests — stores all leave applications with status, dates, priority, and admin comments.
Basic
Q14. How many roles are there in the system? What can each role do? ›
There are two roles: Employee and Admin. Employees can register (pending approval), apply for leave, view their leave balance dashboard, see leave history, cancel pending leaves, view an interactive calendar, and edit their profile. Admins can approve/reject user registrations, create and manage leave types (add, edit, deactivate), manage departments, approve or reject leave requests with comments, and view reports broken down by type, department, and employee.
Basic
Q15. What is a Single Page Application (SPA)? ›
A Single Page Application is a web app that loads a single HTML page and dynamically updates the content using JavaScript without full page reloads. When you navigate from Dashboard to Apply Leave, the browser does NOT load a new HTML file from the server — Vue Router intercepts the click, renders the correct Vue component, and only fetches the needed data (JSON) from the API. This makes the app feel fast and smooth, like a desktop application. The trade-off is that initial load may be slightly slower since the entire JavaScript bundle is downloaded once.

🟡 Intermediate Level — Features & Design

Workflows, architecture decisions, and feature implementation details

Questions 16–30  ·  15 questions

Intermediate
Q16. Explain the user registration and approval workflow step by step. ›
Step 1: Employee opens the app at localhost:5173 and clicks the "Register" tab. Step 2: They fill in their name, email, and optionally select a department and click Register. Step 3: The frontend sends POST /api/users with role='employee'. Step 4: The backend checks if the email already exists. If not, it creates a user document with status='pending' in MongoDB. Step 5: The employee sees a success message saying "Account pending admin approval." Step 6: The admin logs in, goes to Manage Users or the Dashboard, and sees the pending user in a list. Step 7: Admin clicks Approve — the backend sets status='approved' AND automatically reads all active leave types and creates a leave_balances array inside the user document. Step 8: The user now appears in the Select User dropdown and can log in.
Intermediate
Q17. How is leave balance deducted when a leave is approved? ›
When the admin approves a paid leave request, the backend uses MongoDB's $inc operator to atomically update the user's leave_balances array. Specifically, it finds the embedded sub-document where leave_type_id matches the request's type_id and performs: used_days += total_days and remaining_days -= total_days. This is a single atomic database operation, meaning it cannot be partially applied. The $inc operator is critical here because it prevents race conditions — if two leaves were approved simultaneously, simple read-modify-write would give wrong results, but $inc is atomic. Unpaid leaves skip this step entirely since they don't consume paid balance.
Intermediate
Q18. How is leave priority automatically assigned? ›
Priority is assigned server-side in the leaveRequestController.js getPriority() function. It checks the leave type name (lowercased) against keywords: if it includes 'sick', 'medical', or 'emergency' → priority = 'high'. If it includes 'casual' → priority = 'medium'. All others (like Annual Leave) → priority = 'low'. This logic runs on the backend so employees cannot manipulate their own priority by changing the request. On the Admin dashboard, pending requests are sorted: high → medium → low, ensuring urgent leaves like Sick Leave or Emergency Leave are reviewed first.
Intermediate
Q19. How are working days calculated? Why exclude weekends? ›
The countWeekdays() function in leaveRequestController.js iterates through every calendar day from start_date to end_date. For each date, it calls JavaScript's getDay() method — which returns 0 for Sunday and 6 for Saturday. If the day is not Sunday or Saturday (i.e., it's Monday–Friday), the counter increments. Weekends are excluded because employees don't work on weekends, so a leave from Friday to Monday = 2 working days, not 4 calendar days. If the entire selected range falls on a weekend (e.g., Saturday–Sunday), the backend returns a 400 error: "No working days in selected range." The same calculation runs in the frontend for live preview as the user picks dates.
Intermediate
Q20. What is Pinia? Why is state management needed in Vue? ›
Pinia is the official state management library for Vue 3. State management is needed because in a multi-page SPA, some data needs to be shared across all components — in this case, the currently logged-in user's data (name, _id, role, leave_balances). Without Pinia, when the user navigates from Dashboard to Apply Leave, the user's data would be lost because each component is independent. Pinia provides a centralised store that any component in the app can read from. The store also persists the user data to localStorage, so if the browser is refreshed, the user session is restored from storage instead of asking the user to log in again.
Intermediate
Q21. What is Vue Router? How does it work? ›
Vue Router is the official client-side routing library for Vue 3. It maps URL paths to Vue components. In this project, routes are defined in router/index.js — for example, /employee/dashboard maps to the Dashboard.vue component. When a user clicks a navigation link, Vue Router intercepts the event, updates the browser's URL using the History API, and renders the matching component inside the <router-view /> placeholder — all without a full page reload. Routes are lazy-loaded using dynamic import() — the code for each view is only downloaded when that route is first visited, improving initial load performance.
Intermediate
Q22. What is Axios and why use it instead of the built-in fetch API? ›
Axios is a promise-based HTTP client for JavaScript. In this project, a shared Axios instance is created in api/axios.js with the base URL set to '/api'. All API calls use this instance. Axios is preferred over the native fetch API because: (1) it automatically parses JSON responses (no need for .json() call), (2) it provides better error handling (non-2xx status codes throw errors automatically), (3) the shared instance with a base URL means every component just calls api.get('/users') instead of the full URL, and (4) interceptors can be added later (e.g., for authentication tokens) without changing every call.
Intermediate
Q23. What is Vite? What is the proxy configuration and why is it needed? ›
Vite is an ultra-fast frontend build tool and development server. It provides instant Hot Module Replacement (HMR) — when you save a Vue file, the browser updates without a full reload, preserving state. The proxy in vite.config.js is configured so that any request from the frontend to /api is forwarded to http://localhost:5000. This is needed because the frontend runs on port 5173 and the backend on port 5000. Browsers block cross-origin requests (CORS policy). The Vite proxy makes the frontend and backend appear to be on the same origin during development. In production, a reverse proxy (like Nginx) would serve the same purpose.
Intermediate
Q24. What is CORS and why did you enable it on the backend? ›
CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks web pages from making HTTP requests to a different domain/port than the one that served the page. Since the Vue frontend (port 5173) makes requests to the Express backend (port 5000), they are on different ports — which counts as different origins. Without CORS enabled, the browser would block all API calls. In the backend server.js, the cors npm package is added as middleware: app.use(cors()). During development, this is acceptable. In production, CORS should be restricted to specific allowed origins for security.
Intermediate
Q25. What is Mongoose? Explain its key features. ›
Mongoose is an ODM (Object Document Mapper) for MongoDB and Node.js. Key features: (1) Schema definition — you define the structure of documents upfront (field names, types, required fields, enums). For example, the User schema enforces that role must be 'employee' or 'admin'. (2) Validation — Mongoose validates data before saving, preventing invalid data from reaching the database. (3) Middleware — you can add pre/post hooks (e.g., hash a password before saving). (4) populate() — allows referencing documents in other collections and auto-joining them, similar to SQL JOINs. (5) Query API — a chainable, expressive API for building MongoDB queries.
Intermediate
Q26. What is soft delete? Why is it used for leave types? ›
Soft delete means marking a record as inactive (is_active = false) instead of permanently removing it from the database. For leave types, a hard delete would cause problems because existing leave_requests reference the leave type's name and ID. Deleting the leave type would leave orphaned references. With soft delete: deactivated leave types are hidden from the "Apply Leave" dropdown (only active types are shown to employees), but all historical leave requests that referenced that type remain intact and queryable. Admins can also reactivate a type if needed. This preserves historical data integrity.
Intermediate
Q27. What happens when a user selects their account on the home screen? ›
On the SelectUser.vue page, the app calls GET /api/users?status=approved to fetch all approved users. The user picks their name from a dropdown. When they click "Continue", the selected user object (including name, _id, role, dept_id, leave_balances) is saved to the Pinia store using store.setUser(). The store also persists this to localStorage. Vue Router then redirects based on role: if role='admin' → /admin/dashboard, if role='employee' → /employee/dashboard. All subsequent pages read the current user from the Pinia store.
Intermediate
Q28. How does the leave calendar work? ›
The LeaveCalendar.vue page fetches the current user's approved leave requests from GET /api/leave-requests/my/:user_id. It then builds a monthly calendar grid (7 columns for Mon–Sun). For each day in the month, it checks if any approved leave request covers that date. If yes, it renders a colored dot using the leave type's color_code. Users can navigate between months using Previous/Next buttons. Below the calendar grid, a list of approved leaves for the current month is shown with dates and type names. This gives employees a visual overview of their approved leave.
Intermediate
Q29. What is denormalization? Where is it used in this project? ›
Denormalization means storing redundant copies of data to improve read performance, at the cost of some write complexity. In this project, two fields are denormalized: (1) leave_type_name is stored directly in every leave_request document, even though it could be looked up via type_id. This means displaying leave history doesn't require a JOIN with the leave_types collection. (2) leave_balances is embedded inside the user document rather than in a separate collection. This allows fetching a user and their complete balance in a single query. The trade-off is that if a leave type's name changes, existing request records won't auto-update — but for this system, that's acceptable.
Intermediate
Q30. What is the purpose of the seeds/seedData.js file? ›
The seed file is used to populate the database with initial test data. It first clears all existing data (deletes all users, departments, leave_types, and leave_requests), then inserts: 4 departments (Engineering, Marketing, HR, Finance), 5 leave types (Annual 15 days, Sick 10 days, Casual 7 days, Maternity 90 days, Emergency 3 days), and 5 test users (1 admin with status=approved, 3 employees with approved status and pre-filled leave balances, 1 pending employee). It is run with node seeds/seedData.js from the backend folder. This makes it easy to reset the database to a clean state for testing or demonstration.

🔴 Advanced Level — Technical Deep Dive

Internals, algorithms, trade-offs, and production readiness

Questions 31–45  ·  15 questions

Advanced
Q31. Explain the MongoDB Aggregation Pipeline used for department stats. ›
The department stats use a 6-stage aggregation pipeline: Stage 1: Start with the leave_requests collection. Stage 2: $lookup with users collection (join on user_id = _id) — attaches user data to each request. Stage 3: $unwind the users array — flattens it so each document has exactly one user object. Stage 4: $lookup with departments collection (join on user.dept_id = _id) — attaches department data. Stage 5: $unwind with preserveNullAndEmptyArrays: true — this is critical: it keeps requests from users with no department assigned (they go into a 'No Department' group) instead of being dropped. Stage 6: $group by department name using $ifNull to handle nulls, computing sum of totalRequests, totalDays, and conditional counts for approved/pending/rejected using $cond. Stage 7: $sort by totalRequests descending. The result is an array like [{ _id: "Engineering", totalRequests: 5, totalDays: 12, approved: 3, pending: 1, rejected: 1 }].
Advanced
Q32. What is a race condition? How does MongoDB's $inc prevent it? ›
A race condition occurs when two operations happen simultaneously and both depend on reading the same value before writing. Example without $inc: Request A reads user's remaining_days = 10. Request B also reads remaining_days = 10. Request A calculates 10 - 3 = 7 and writes 7. Request B calculates 10 - 5 = 5 and writes 5. Final result: 5, but should be 2 (10 - 3 - 5). With MongoDB's $inc: the operation remaining_days: -3 is a single atomic increment instruction sent to MongoDB. MongoDB applies it at the database level in one operation. Even if two requests arrive simultaneously, MongoDB queues the $inc operations. Each one reads the current value and applies the increment atomically. The result is always correct.
Advanced
Q33. What is the Composition API in Vue 3? How is it different from the Options API? ›
The Composition API is a set of APIs in Vue 3 that allows organizing component logic by feature rather than by option type. The traditional Options API organizes code into sections: data(), methods(), computed(), mounted(), etc. In a large component, related code for one feature gets split across multiple sections. The Composition API uses <script setup> syntax (used throughout this project) with functions like ref(), computed(), onMounted() directly in the setup context. All variables and functions related to one feature can be grouped together. Benefits: better code organization, easier reuse via composables, full TypeScript support, and slightly better performance due to smaller component instance.
Advanced
Q34. Explain the $lookup stage in MongoDB. How is it similar to SQL JOIN? ›
$lookup is a MongoDB aggregation stage that performs a left outer join with another collection. Syntax: { $from: 'target_collection', $localField: 'field_in_current', $foreignField: 'field_in_target', $as: 'result_array_name' }. It is similar to SQL's LEFT JOIN — for each document, it finds all matching documents in the target collection and attaches them as an array. In this project, $lookup joins leave_requests with users (matching user_id to _id) and then users with departments (matching dept_id to _id). The key difference from SQL JOIN: MongoDB $lookup results in an embedded array, so a $unwind stage is needed to flatten it back to one document per result. Also, $lookup works on denormalized data without foreign key constraints.
Advanced
Q35. What is the difference between ref() and reactive() in Vue 3? ›
Both are reactivity APIs in Vue 3. ref() wraps a primitive value (string, number, boolean) or object in a reactive reference object. You access the value via .value in JavaScript (e.g., count.value++) but Vue templates automatically unwrap it (just use {{ count }}). reactive() wraps a plain object and makes all its properties reactive. You access properties directly without .value. In this project, ref() is used for most state (e.g., const users = ref([]), const loading = ref(false)) because it works with both primitives and objects. reactive() is typically used when you have a group of related values that belong together.
Advanced
Q36. How does Vite's Hot Module Replacement (HMR) work? ›
HMR allows Vite to update modules in the browser without a full page reload. When you save a .vue file, Vite's dev server: (1) detects the file change via the file system watcher. (2) Compiles only the changed module. (3) Sends the updated module to the browser over a WebSocket connection. (4) The browser replaces only the changed component in the running app, preserving the current state (e.g., if you were on the Apply Leave page, you stay there with your form data intact). This dramatically speeds up development compared to the traditional save → full reload cycle.
Advanced
Q37. What is lazy loading in Vue Router and why is it important? ›
Lazy loading means the JavaScript code for a route's component is only downloaded when that route is first visited, instead of bundling everything into one large file that must load before the app starts. In this project, all routes use dynamic imports: component: () => import('../views/employee/Dashboard.vue'). The parentheses with () => make this a function that returns a promise — Vite treats this as a code-split point and creates a separate chunk. Benefits: the initial bundle (first load) is smaller and loads faster. If an admin never visits employee routes, that code is never downloaded. Vite handles the bundling automatically.
Advanced
Q38. What is the event loop in Node.js? Why is Node.js non-blocking? ›
The event loop is the core mechanism that allows Node.js to perform non-blocking I/O despite JavaScript being single-threaded. When Node.js encounters an I/O operation (like a MongoDB query), instead of blocking the thread and waiting for the result, it registers a callback and moves on to handle the next request. When the I/O operation completes, the event loop picks up the callback and executes it. This is why Node.js can handle thousands of concurrent API requests efficiently — it never sits idle waiting for I/O. In this project, all database operations (Mongoose queries) are async/await — they are non-blocking under the hood.
Advanced
Q39. What is async/await? How does it work? ›
async/await is syntactic sugar over JavaScript Promises that makes asynchronous code look and behave like synchronous code. An async function always returns a Promise. The await keyword pauses execution inside the function until the Promise resolves, then returns the result. In this project, all controller functions are async — e.g., const user = await User.findById(id) waits for the MongoDB query to complete before continuing. Error handling is done with try/catch blocks. Without async/await, the same code would use .then().catch() chains, which are harder to read and maintain. The underlying async nature (non-blocking event loop) is unchanged.
Advanced
Q40. Why are leave_balances embedded in the user document rather than a separate collection? What are the trade-offs? ›
leave_balances are embedded for three reasons: (1) Access pattern — they are always read together with the user (the Dashboard shows all balances). Embedding avoids a separate query. (2) Atomic update — the $inc operation to deduct balance targets one document. With a separate collection, a multi-document update would need a transaction. (3) Bounded size — the number of leave types is small and bounded. Trade-offs of embedding: if a leave type's max_paid_days changes, all user documents need to be updated individually (no cascade). Also, if there were hundreds of leave types, embedding would bloat user documents. A separate collection would be better in that case. This design decision prioritises read performance and atomic updates over update simplicity.
Advanced
Q41. What are HTTP status codes? Which ones does this project use? ›
HTTP status codes indicate the result of an HTTP request. This project uses: 200 OK — successful GET/PUT requests. 201 Created — successful POST (new resource created, e.g., new user or leave request). 400 Bad Request — client-side validation error (e.g., insufficient leave balance, duplicate email, no working days in range). 404 Not Found — requested resource doesn't exist (e.g., user ID not found). 500 Internal Server Error — unexpected server error (database connection issue, etc.). Using correct status codes is important because frontend code can check the status code to decide how to handle the response — showing a success message for 201, an error alert for 400, etc.
Advanced
Q42. What is middleware in Express.js? Name the middleware used in this project. ›
Middleware is a function that has access to the request (req), response (res), and the next middleware function (next). Middleware runs between the request arriving and the route handler executing. In this project: (1) cors() — handles Cross-Origin Resource Sharing headers. (2) express.json() — parses incoming JSON request bodies so controller functions can access req.body. (3) Error-handling middleware — defined at the end of server.js with 4 parameters (err, req, res, next), catches any errors thrown in route handlers and returns a 500 response. Middleware runs in order — if cors() or express.json() isn't added before routes, the routes won't work correctly.
Advanced
Q43. What is the difference between findById(), findOne(), find(), and findByIdAndUpdate() in Mongoose? ›
find() — returns an array of all documents matching a filter. Used in getAllUsers, getAllLeaves. findOne() — returns the first document matching a filter. Used in createUser to check if email exists. findById(id) — shorthand for findOne({ _id: id }). Used to fetch a specific user or leave request before updating. findByIdAndUpdate(id, update, { new: true }) — finds a document by ID, applies the update, and with { new: true } returns the updated document (without { new: true } it returns the original). Used in rejectUser and updateUser. The difference matters because findByIdAndUpdate runs a single DB operation while findById + save runs two.
Advanced
Q44. What is the $cond operator in MongoDB? How is it used in the aggregation pipeline? ›
$cond is MongoDB's conditional operator, similar to a ternary expression: { $cond: [condition, value_if_true, value_if_false] }. In the department stats aggregation, it counts approved/pending/rejected requests within the $group stage without multiple queries: approved: { $sum: { $cond: [{ $eq: ['$status', 'approved'] }, 1, 0] } } — for each document, if status equals 'approved', add 1, otherwise add 0. This effectively counts approved requests per group in a single pass through the data. Without $cond, you'd need three separate aggregation queries (one for each status), which would be three times slower.
Advanced
Q45. What improvements would you make to this project to make it production-ready? ›
Several improvements are needed for production: (1) Authentication — add bcrypt password hashing and JWT (JSON Web Tokens) for secure login. Currently any user can select any account. (2) Authorization middleware — verify JWT on protected routes instead of trusting the frontend. (3) Input sanitization — sanitize all inputs to prevent NoSQL injection. (4) Rate limiting — use express-rate-limit to prevent API abuse. (5) HTTPS — deploy with SSL/TLS certificates. (6) Restrict CORS — allow only specific trusted origins, not all. (7) Environment-specific configs — separate dev/prod MongoDB URIs. (8) Logging — use Winston or Morgan for structured logging. (9) Docker — containerize both backend and frontend for consistent deployment. (10) CI/CD — automated testing and deployment pipeline.
